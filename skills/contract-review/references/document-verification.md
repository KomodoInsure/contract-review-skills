# Document execution and verification

Use a tool whose capabilities match the deliverable. Text proposals and native Word redlines are different artifacts. Before editing, preserve an original or work on a separate output copy unless the user explicitly requests in-place edits. Identify existing revisions, author attribution, comments, tables, numbering and cross-references.

Apply exact anchored edits through the available document workflow. Anchor to both location and distinctive text where repetition creates ambiguity. Verify the tool's per-edit result. If a batch partially succeeds, retry only failed operations; do not duplicate already-applied edits. Re-read the current document before repairing an anchor.

Preserve the meaning and attribution of prior revisions. Do not silently accept or reject all changes to simplify editing. If the tool cannot reliably preserve a required feature, provide proposed edits and state the limitation instead of claiming a completed redline.

Verify the saved artifact, not just the edit request: opens successfully; intended insertions/deletions and comments appear; correct author; no unintended changes; references and numbering intact; final accepted-text reading is coherent; promised files exist. On acceptance-only turns, do not invent substantive changes just to make a file look reviewed.

Assess minimality substantively as well as mechanically. A tool may represent a small insertion as deletion and reinsertion of a longer anchor. That diagnostic is not proof that the legal change was broad. Report tool artifacts separately from the scope of the intended change.

If no suitable document tool is available, deliver a table of location, exact existing text, proposed replacement and rationale. Label it as proposed edits; do not call Markdown strikethrough a native Word redline.
